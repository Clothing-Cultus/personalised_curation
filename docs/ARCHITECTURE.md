# Architecture & General FAQ

Living reference for the Personal Curation backend (`personalised_curation/`,
built to spec v9). The FAQ section captures the clarifying questions asked during
development and their answers, so the reasoning isn't lost.

---

## 1. System at a glance

Three separated layers, one shared foundation:

- **`core/`** — shared, framework-free foundation imported by both `app/` and
  `ml/`. Holds `config.py` (every tunable number + the structured-block layout),
  plus small helpers: **normalize** (canonical values / hex→rgb / size-stock),
  **logging**, **errors** (domain exceptions → HTTP status, so services never
  import FastAPI), **auth** (the single shared-secret check).
- **`ml/`** — the nightly pipeline. Loads catalog → CLIP image+text embeddings →
  per-feature MDS structured block (all 12 similarity matrices) → one
  L2-normalized `product_matrix.npy` + meta + clusters + anchor deck. Never
  imports `app/`.
- **`app/`** — the FastAPI service (MVC: controllers → services → repositories).
  Serves swipe decks and learns per-user taste. Reads `ml/artifacts/` only.

Recommendation = `cosine(user_vector, product_matrix)` + business nudges −
penalties → MMR diversify → Thompson-sampling explore.

## 2. Data model

**5 new tables** (`migrations/001_pc_tables.sql`): `user_taste`, `pc_sessions`,
`pc_session_items`, `pc_purchase_weights`, `pc_job_runs`.
**Existing tables are read-only** — never altered or written by the code
(Hard Rule #1).

## 3. Key files

| Path | What |
|---|---|
| `ml/artifacts/product_matrix.npy` | the shared product matrix (all users) |
| `ml/reference_data/.../*.csv` | the 12 similarity matrices the pipeline reads |
| `core/config.py` | every tunable + structured-block layout |
| `app/services/scoring_service.py` | filter → score → diversify → explore |
| `app/services/taste_service.py` | the reusable vector-update function |
| `migrations/001_pc_tables.sql` | the 5 new tables (run manually) |

## General FAQ

### `curator/` vs `personalised_curation/`
`curator/` is the **old v2 prototype**, kept only for reference. `personalised_curation/`
is the **current v9 build** — the one being deployed. v9 differences: `core/config.py`
constants (not YAML), strict MVC + separate `ml/` tree, all 12 matrices → MDS
(not just `fashion_sub_style`), the renewal session model, and the new table set.
`curator/` can be ignored/deleted with no effect.

### Where is `category.csv` (and the matrices)?
The pipeline reads the **in-repo copy**:
`ml/reference_data/Data/Synthetic data/Features similarity matrices/sentence_transformer_manual_04_08_2025/`.
The original lives under `../past data/…/sentence_transformer_manual_04_08_2025/`.
Fix data in the in-repo copy (and keep the original in sync).

### Where is `product_matrix` saved?
`ml/artifacts/product_matrix.npy` — a local file written by the pipeline. Alongside
it: `product_meta.parquet`, `clusters.json`, `anchor_deck.json`, `vibe_vectors.npz`,
`manifest.json`. It is **git-ignored** (regenerated by the pipeline, not committed).
The API loads it into memory at startup and **hot-reloads** within ~60s whenever the
pipeline writes a new version.

### Is the product matrix stored per user? What's stored per user?
**No.** The `product_matrix` is **one shared artifact**, identical for everyone.
Per user we store only the `user_taste` row:

| Field | Meaning |
|---|---|
| `vector` | the taste — one point in product-space (see below) |
| `vector_version` | which matrix build it's compatible with |
| `swipe_count` | how many swipes shaped it |
| `last_decayed_at` | when cross-session decay was last applied |
| `size_preferences` | e.g. `{"topwear":"M","bottomwear":"32"}` |

≈ 2.5 KB per user. Also **in-memory only** (not columns): Thompson-bandit
`cluster_stats` and `price_band_counts` — derived learning state (see TODO to
persist). `pc_session_items` stores the **raw swipe history** (the source the
vector is computed from), which is *not* the taste itself.

### What is the `vector`, in simple words? How is it generated?
Every product is a **point** in a space of numbers (each number ≈ one aspect of
style/color/price/fit). Similar products sit near each other. A user's `vector`
is a **single point in that same space — where their taste lives.**

It starts at zero. Each swipe nudges it:
- right → pull toward the product (+1.0); superlike → pull harder (+2.5);
  left → push away (−0.4).
- after each nudge it's re-normalized (only direction matters, not magnitude);
  old swipes slowly fade (decay) so it tracks *current* taste.

Plain formula: `new taste = normalize(a little of old taste + this swipe's pull
toward/away from the product)`. Recommendations = the products closest to that
point.

### How big is the vector — does it grow with product count?
**No.** The vector length is the number of **features**, not products.
Currently **585** = 512 (blended CLIP image+text embedding) + 73 (structured
block: style, category, design, color, price, fit, …). The `product_matrix` is
`(N_products × 585)`; each user vector is `585`.
- 969 products today → matrix is `(969 × 585)`, user vector `585`.
- 20,000 products later → matrix `(20000 × 585)`, user vector **still 585**.
585 comes from the feature design, and only changes if you add/remove features
(e.g. a new similarity matrix), never from adding products.

### If new products are added, or a product's features change, does the matrix update — and can a user's curated order change?
**Yes.** The nightly pipeline rebuilds `product_matrix`:
- new product → new row → can now appear in decks;
- changed product → its row is re-embedded → it moves in product-space.
Since ranking is `cosine(user_vector, matrix)`, any matrix change can re-order
everyone's recommendations. Not instant — happens on the next pipeline run; the
API hot-reloads it within ~60s. Embeddings are cached, so only new/changed
products re-embed. Adding/editing products does **not** change the vector layout,
so user vectors stay valid.

### If I add/remove a feature, can I recompute all users' taste from their past swipes? Is it expensive?
**Yes — that's the replay job**, and it's cheap. Because `taste_service.apply_interactions`
is one reusable function, you replay each user's `pc_session_items` history
through it against the new matrix to rebuild their vector. Each swipe is a tiny
585-dim vector op; even 100k users × 100 swipes ≈ 10M ops — seconds to minutes,
not a heavy job. This is *why* full swipe history is stored (the vector is a
cache of it). Live behavior on a version change is cold-start-immediately (no
lag); the replay job restores vectors offline. The function exists now; running
the batch job is deferred (PC-todo-later §5).

### After a feature change, does the user really cold-start, or come back to a vector rebuilt from past swipes?
The **intended** design is: come back to a vector rebuilt from their past swipes
(not the initial deck) — but with two caveats:
1. **The replay job isn't built yet (deferred).** So *today*, a `vector_version`
   mismatch gives a **true cold-start**.
2. Even once built, the **live** path always cold-starts *instantly* (rebuilding
   synchronously would add request latency); the **replay job** rebuilds the
   vector offline from `pc_session_items` history and writes it back.
So a user active in the window *between* the feature change and the replay job
sees cold-start; after the job runs they're fully personalized. **Best practice:**
run the replay job in the **same nightly job** that changes features, so by the
time users return their vectors are already rebuilt — they never practically see
cold-start. Until the replay job is built, a feature change is a genuine cold-start.

### Does the pipeline run every night?
Yes — it's designed as a **nightly cron** (~2 min). In dev it's run manually
(`python -m ml.pipeline.run_pipeline`); in prod it's scheduled. It can also be
run on-demand after a bulk catalog change. The API hot-reloads the new version
within ~60s. Pair a feature/weight change with a pipeline run (and, later, the
replay job) in the same night.

### In prod, where should `product_matrix` live — EC2 or Supabase/S3?
The API loads it into **RAM** for fast scoring, so it must sit on **fast local
disk read at startup** — the **EC2 instance's local disk** (pipeline writes,
API reads). Supabase Storage/S3 is **not** in the hot path.
- **Now / single instance:** keep it on EC2 local disk (or a shared EBS volume if
  the pipeline and API run on separate boxes).
- **Later / multiple API instances:** run the pipeline once, upload the artifact
  to S3 (or Supabase Storage), and have each API instance download it on reload —
  S3 as the shared distribution point; each instance still holds a RAM copy.
Keeping a backup copy in S3 is worthwhile regardless.

### Where are the vector-replay job and collaborative filtering used?
**Replay job is now built** (`scripts/rebuild_user_vectors.py`, run after the
pipeline by `scripts/nightly.py`) — it replays each user's `pc_session_items`
history through `taste_service.rebuild_vector` onto the new matrix (verified to
produce the same vector as the live path). Fully effective once
`ENABLE_DB_WRITES=True`. **Collaborative filtering is still future** — deferred
until ~50k+ interactions; would slot into `scoring_service` as a pluggable
`0.6·content + 0.4·collab` blend.

### What happens to cards a user was served but never swiped (left mid-session)?
They're **recycled**. In a swipe UX you can't advance without swiping, so an
un-swiped served card is one the user *never reached* (it sat in the client
buffer). When the user returns — resume of the same session OR a new session
after renewal — `_serve_at_start` re-offers those un-swiped cards **first** (via
`items.owed_product_ids` + `scoring_service.recycle_cards`, re-validated against
current stock/gender/size), then fills the rest with fresh recommendations.
Nothing is wasted. `cards_served` is recomputed from the DISTINCT served set, so
re-offered cards don't double-count. Active-session refills do NOT recycle (the
client still holds that buffer). The full impression log (every served row,
swipe=NULL until swiped) is kept for analytics.

### What debug signals does the service log?
Beyond errors: **`products_swiped` divergence** (frontend's advisory count vs. the
backend's authoritative `cards_swiped` — client should re-sync to `total_swipes`),
**duplicate swipe ignored** (idempotency hit), **swipe on a product not in the
matrix** (skipped from the vector), and **refill served 0 candidates** (pool
exhausted for that user's filters). All at INFO. Candidate future adds: request
latency, cold-start/version-mismatch events, per-session end reasons.

### Where are the swipe / purchase weights stored?
In **`core/config.py`**, NOT the database (Hard Rule #8 — every tunable is a
git-versioned constant, never inline or in a DB table). Two dicts:
`SWIPE_WEIGHTS` = `{right: +1.0, superlike: +2.5, left: -0.4, left_engaged: -0.1}`
and `PURCHASE_WEIGHTS` = `{gift: +1.0, unknown: +3.5, self: +5.0}`. Change a
number there → it takes effect on the next process start (weights are read at
scoring/update time). To live-A/B them later you'd move them to a DB config
table, but that's deliberately deferred (spec §3).

### Do right-swipes and superlikes share a counter?
**No — they're independent.** A right-swipe increments `rights_used` only (cap
`RIGHTS_LIMIT`=8); a superlike increments `superlikes_used` only (cap
`SUPERLIKES_LIMIT`=1). A superlike does NOT consume a right. So a session can
have up to 8 rights *plus* 1 superlike. Session end (`rights_exhausted`) triggers
on right-swipes alone; superlikes never end the session. Both still count as a
swiped card (`cards_swiped`) and both move the taste vector (right +1.0,
superlike +2.5).

### Why are in-session purchases weighted by the nightly job, not live like swipes?
A swipe is an immediate, final taste signal, so it moves the vector on the spot.
A **purchase isn't final at swipe time** — payment can fail, the order can be
cancelled or returned. So the nightly job weights purchases from the **confirmed**
`orders`/`order_items`, applied **exactly once** via the `pc_purchase_weights`
idempotency ledger — crediting only real completed purchases and never
double-counting. The trade-off: an in-session buy doesn't nudge that same
session's recommendations. `bought_in_session` / `bought_as_gift` are recorded on
`pc_session_items` for the nightly job to consume. (If we ever want an immediate
in-session nudge, treat the buy as a right/superlike-strength live signal and have
the nightly job skip items already credited in-session — deliberately not done
now, to keep purchase weighting single-sourced.)

### How does size selection work (`size_selected` + `size_default_for_category`)?
Each `ProductInteraction` carries **`size_selected`** (e.g. `"M"`, `"32"`) and
**`size_default_for_category`** (bool). If `size_default_for_category` is **true**,
the size is written into `user_taste.size_preferences` (e.g. `{"topwear":"M"}`) and
feeds the size FILTER — future cards for that garment type are restricted to that
size. If **false**, it's a one-off for this product only (logged, no future
effect). The frontend sets the bool from an explicit UI choice ("my size for all
tops" vs "just this item"); the backend never guesses it. Internally the DB keeps
the existing `pc_session_items.size_scope` text column (`category` /
`this_product`), derived from the bool — so the API contract changed without a DB
rename. Purpose: size-aware feed without being annoying — set your size once, still
try a one-off size on a specific item.

### What are `score` and `percent_match`, and why are their values so different?
`score` is the **internal ranking number**: `cos(u,P)` + business nudges (price
band, bestseller, newness) − penalties (brand fatigue, seen-similar, recency).
It's a small raw float (~0.1–0.5, can be negative), used only to ORDER products,
never shown. `percent_match` is the **user-facing taste-match %** — NOT
`score × 100`, but the **percentile rank** of that score within the current
candidate pool, mapped into the 58–97 band. So raw scores clustered around
0.1–0.4 still display as a readable 58–97% spread (best pick ≈97%, weakest ≈58%).
Raw cosine reads badly as a percentage (a great pick might be cosine ~0.35 →
"35%"), so we rescale by rank. Both are stored on `pc_session_items` so the
display method can be recalibrated later (rescaling is an open tuning item).

### Is the gender filter a hard guarantee?
Yes. Every candidate passes a **hard gender filter** (`scoring_service._gender_ok`,
always on via `GENDER_SCOPE`): a **male** user is only ever shown `{male, unisex}`,
a **female** user only `{female, unisex}`, and an **unknown / prefer-not-to-say**
user only `unisex`. Tokens are canonicalized (male/men/M → male, female/women/W →
female…) so a spelling mismatch can't defeat it. A NULL/unrecognized product
gender is treated as unisex (never 'female'/'male'), so it can never leak a
female item to a male user or vice-versa. A future onboarding question can let a
user opt into seeing the other gender (TODO); default is own-gender-only.

### When does a rebuild / cold-start actually happen? (version vs. layout_signature)
The manifest carries **two** identifiers:
- **`version`** — a per-run timestamp. Changes every pipeline run. Used only for
  hot-reload detection (the API notices a new build).
- **`layout_signature`** — a hash of the feature layout (block names + dims +
  total dim). Changes **only** when a feature is added/removed or a block's size
  changes — NOT when products or values change.
User-vector compatibility is keyed to **`layout_signature`**, so:
- product-only / value-only nightly run → same signature → every vector stays
  valid → **no cold-start, rebuild finds 0 stale users**;
- feature added/removed → new signature → those vectors are stale → the live path
  cold-starts and the rebuild job replays them onto the new matrix.
So a rebuild is only ever needed when the feature set changes — exactly as
intended.

### What is "hot reload"?
The API holds the product matrix in memory. A background thread checks
`manifest.json`'s `version` every ~60s; when the pipeline publishes a new
version, the API loads the new artifacts and **atomically swaps** the in-memory
bundle under a lock — **no server restart, no downtime, no dropped requests**.
Because the swap is atomic and the manifest is written last, requests in flight
keep using the old matrix until the new one is fully ready. That's how a nightly
rebuild takes effect within a minute without anyone noticing.

### How do we keep users swiping DURING the nightly job from cold-starting?
Layered defenses (all in place):
1. **Atomic swap** — during the pipeline run the OLD matrix keeps serving; the
   new one only goes live after it's fully written and reloaded. No disruption
   mid-run.
2. **Layout-unchanged vectors stay valid** — a run that only adds products or
   edits values keeps the same `layout_signature`, so every vector remains valid
   → **no cold-start at all**. Only adding/removing a feature changes the layout.
3. **Layout-aware hot-reload** — the reload thread auto-swaps only **same-layout**
   builds. A build that changes the feature layout is **NOT auto-adopted**; it
   logs a warning and keeps serving the current matrix until a deliberate restart.
   So a feature change can't sneak in mid-day and cold-start everyone.
4. **Replay-before-promote — achieved via the sequence, not extra machinery.**
   For a feature change: run `scripts/nightly.py` (pipeline + vector-rebuild →
   writes new vectors to the DB), **then** restart the API. On restart it loads
   the new matrix AND the already-rebuilt vectors together → **zero cold-start
   window**. This IS replay-before-promote (rebuild first, adopt second), so an
   explicit staging/promote mechanism would be redundant complexity — deliberately
   not built.

Remaining idea (not built): **lazy inline replay on read** — if a user ever hits
with a stale vector, rebuild it inline from recent history in a few ms instead of
zeroing. Only relevant if you ever adopt a layout change without a restart.

**Operational rule:** ship feature/layout changes through a **deliberate restart
after the nightly rebuild**, never via hot-reload.

### Where should artifacts live in staging/prod, and how do instances share them?
The pipeline can publish artifacts to **Supabase Storage** (bucket `pc`, folder
`artifacts/`) and each API instance downloads them locally on reload — code is
written but **dormant** (call sites commented) for local dev, which reads
`ml/artifacts/` directly. Enable for staging/prod (see TODO): create the `pc`
bucket, uncomment the upload in `run_pipeline` and the download in
`artifact_store`. Each instance still holds the matrix in RAM for the hot path;
Storage is just the shared distribution point.

### What does "re-run the pipeline" mean?
Run `python -m ml.pipeline.run_pipeline`. It reloads the catalog, re-embeds
new/changed products, rebuilds `product_matrix` + meta + clusters, and writes a
new artifact version. The API auto-picks-up the new version within ~60s. You
re-run it whenever catalog data changes or you change features/weights.

### Why the `ENABLE_DB_WRITES` switch + JSONL spool?
It honors the rule **"no migration/DB change by code; I run migrations manually;
never touch prod"** (Hard Rule #2 + explicit instructions during development).
The app must run fully **before any tables exist**. So:
- `False`: nothing reaches Supabase; every event is appended to
  `data/spool/*.jsonl` and in-memory state serves the live session — no data lost.
- `True` (after you run the migration): events also write to the real tables, on
  a background thread so a swipe never waits on the DB.
- `scripts/replay_spool.py` backfills anything captured while writes were off.
One boolean, one funnel (`repositories/base.py → Gateway`), so writes can't leak.

### Which existing tables change? Do we add columns?
**No existing table is altered by code.** Two column notes:
- `topwear.hooded`, `bottomwear.fade`, `bottomwear.closure_type` — **confirmed to
  already exist in prod** and are used in the structured block.
- `products.ai_features_extracted` — a **future** column (TODO): mark whether AI
  feature extraction ran, and include a product in the matrix only if true. You'd
  add this by hand when that feature is built.

### What was Docker for?
Running a **local Supabase** (via the Supabase CLI, which uses Docker) so all
testing/setup happens against a local clone of prod's schema + some product data
— production never read or written by the app. See `docs/LOCAL_SETUP.md`.
